### <a name="_qmphm5d6rvi3"></a>**Описание очередности выделения сервисов с обоснованием логики**

Для разбиения монолита на микросервисы по доменным моделям Booking, Driver, Pricing, Payments, Notification, Geography, Fraud, можно использовать такую последовательность отделения моделей:
В процессе вынесения сервисов потребуется создание ACL для преобразования запросов в формат монолита и возможности переключения получателя запросов

1. Настройка брокера сообщений Kafka
2. Вынесение приложения сервиса Fraud, как наиболее влияющего на безопасность транзакций, проверки на фрод необходимо проводить в независимом по нагрузке сервисе
3. Выделение сервиса Payments также по соображениям безопасности
4. Выделение сервиса Notification, как наименее связанный с основными доменными областями
5. Выделение сервиса Booking, т.к. основная нагрузка будет именно на этот сервис и необходимо выделять его после сервисов влияющих на безопасность (запросов пользователей больше чем запросов водителей, и пользовательский опыт(скорость отклика пользователя) важнее пользовательского опыта водителей)
6. Выделение сервиса Pricing На этот сервис тоже будет большое количество нагрузки, поэтому он выделен раньше менее нагруженных
7. Выделение сервиса Geography Оставшиеся сервисы выделяем в любом порядке, предлагаю начать с Geography, чтобы закончить переносом большого сервиса Driver 
8. Выделение сервиса Driver

### <a name="_bjrr7veeh80c"></a>**План миграции**

1. Необходимо реализовать ACL для возможности переключения запросов между выделенными сервисами и монолитом
2. Реализация Gateway API
3. Выделение микросервисов в порядке описанном выше, при выделении микросервиса также формируем обвязку микросервиса в виде выделения базы данных, кэш хранилища, celery worker, и переключения взаимодействия с RabbitMQ на Kafka Broker. После реализации нового микросервиса необходимо настроить частичное переключение трафика на новый микросервис, для анализа работоспособности модели.
4. Деактивация ACL
